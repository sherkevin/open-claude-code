# 飞书项目群入口

这个独立目录把一个飞书应用机器人、一个指定群，绑定到**已经打开的 Codex 会话**。它不创建 Claude 或 Codex 新会话，不修改本项目产品服务。当前部署的应用显示名为 `dengkw-华微世纪`，独立 profile 名为 `dengkw-华微世纪负责人`；仓库示例默认关闭。

截至 2026-11-10，版本 `1.0.3` 已发布，服务已启用并建立飞书长连接，首条真实群 @ 已进入指定会话执行并成功回复到群里。普通消息静默、非空群历史与线程、其他成员 @ 和并发输入等实际场景仍待进一步验证。实际身份、检查结果和验收回执见 [部署记录](DEPLOYMENT.md)。

## 消息如何流转

```text
指定项目群的人明确 @ 本机器人
    → lark-cli 指定 profile、bot 身份
    → 持久 inbox（message_id 去重）
    → 读取该群近期消息、关联父消息、线程及成员
    → 既有 Codex 会话空闲后，按收到的顺序提交
    → 精确匹配该任务的原生 turn 和 final
    → 只取显式的公开回复信封
    → 持久 outbox
    → 机器人回复原消息并真正 @ 发起人或本群成员
```

其他群、其他机器人、私聊、只打出机器人名字、@ 全体、普通线程跟帖均不触发任务。普通消息通过群历史读取作为背景，不触发额外回复。暂时只接受带明确 @ 的文字和富文本消息；图片、文件可作为文字任务中的上下文引用，但本模块不会自动下载附件。

电脑上的原会话仍可聊天。会话已有任务、草稿、未消费输入或正在执行的长期目标时，群任务排队，不打断原任务。已经受阻（`blocked`）、暂停（`paused`）或完成（`completed`）的目标本身不再占用空闲会话，但当前轮次、未消费输入、面板空闲和空输入框检查仍须全部通过；其他目标状态默认不投递，也不会为了接收消息而修改目标状态。群任务的运行轮次若混入另一条人工输入，自动群回复会被暂停，避免把私人对话结果转发出去。

## 启动前条件

1. 创建或选中独立应用，配置独立 `lark-cli` profile。当前应用沿用用户设置的显示名 `dengkw-华微世纪`，profile 为 `dengkw-华微世纪负责人`，两者不要求相同。不得把学校大管家的应用当作本应用；示例明确排除了 `cli_aa5e2ae5a638dd0d`。
2. 应用开启机器人、长连接及 `im.message.receive_v1` 事件，并发布可用版本；加入目标群。拥有发送机器人消息、读取群历史与读取群成员等所需权限。具体后台项和当前部署进度见 [部署记录](DEPLOYMENT.md)。
3. 核实目标应用的 `appId` 和 bot `openId`。用户身份和不同应用的 `open_id` 不能混用。程序启动前通过 `whoami --as bot` 和 `auth status --json --verify` 核对两者，不读取或打印明文凭据。
4. 核实已有会话、Orca 工作区及面板、Codex 二进制、工作目录和运行时数据目录。`orca_transport.py` 会验证原会话唯一写入进程及原生会话记录，失败时不新起另一个会话。
5. 确认独立应用只有预期的事件长连接。多个不同客户端连接同一应用可能抢分事件；本模块只锁定自己的本地状态目录，不能检测所有远端订阅者。

使用 Python 3.10 或以上，无额外 Python 依赖。需要本机已安装的 `lark-cli` 和登记过的 Orca 命令。

从仓库根目录运行：

```bash
# 复制示例到私有配置位置，填写真实 profile、app、bot 和 Orca 登记信息。
# 不把应用 secret、access token 写进此配置。
python3 -m integrations.feishu_project_bot /path/to/config.json --check

# 只看本地队列状态；服务运行时也能查看，不连接飞书。
python3 -m integrations.feishu_project_bot /path/to/config.json --status

# 明确设置 enabled=true 后才启动事件订阅及会话投递。
# send_replies=true 才允许回复飞书；false 会将已完成回复保留在 outbox。
python3 -m integrations.feishu_project_bot /path/to/config.json
```

`--check` 只核实身份、读取群历史与成员，不订阅、不发消息、不向会话提交。它不替代对 Orca 原会话的独立只读核实。`send_replies=false` 仍然会向既有 Codex 提交任务，因此离线测试应运行下述单元测试，不能仅靠此开关假定完全无副作用。

监听遵循 CLI 的 stderr ready marker，不靠固定睡眠假定连接成功；父进程保持 stdin 打开以避免 CLI 因 EOF 立即退出。关闭时先关 stdin，必要时发 SIGTERM，不使用 SIGKILL。

## 上下文与回复规则

默认读取触发消息之前最多 40 条群消息。有关联父消息时另外读取；有关联线程时最多翻阅 5 页，越过触发之后的消息，再选择触发之前的背景。无法读取必需历史时任务留待检查，不让智能体假装已看过。长消息和超出大小限制的历史会明确标注截断；总提示词保持在 Orca 传输限制以内。

智能体可以按会话规则输出正常汇报，但必须提供唯一的公开回复对象，允许放在一个 JSON 代码块中：

```json
{
  "feishu_project_reply": {
    "request_id": "由桥接程序提供的精确任务编号",
    "text": "适合在该群公开的结果",
    "mention_ids": ["ou_已核实的群成员"]
  }
}
```

桥接程序只发送其中 `text`，不发送完整 final，不发送工具输出，不同步原会话的其他历史。`request_id` 不匹配、出现多个信封、缺少信封、未知成员、直接拼接 `<at>` 标签均暂停自动发送。群成员从本应用的 bot 身份查询；默认 @ 发起人，可增加经过校验的本群成员。

输入提示明确把群历史当作不可信背景，只授权本项目工作，禁止读取或公开主账号凭据、私人聊天、其他项目资料及执行系统管理要求。**因为执行端是既有高权限会话，这些任务边界属于模型指令约束，不是操作系统级权限隔离。** 如果要向不受信任的外部人员开放，应另行提供受限执行环境，不能宣称共用会话具备完整沙箱隔离。

## 持久化和异常处理

状态存放在配置的私有目录中，包含收到的群任务、输入上下文、公开回复 outbox 和传输收据。状态目录绑定应用、群和会话，修改这些绑定后必须使用新的状态目录，避免旧任务误投给新目标。日志只记录状态与错误类别，不主动打印任务正文。

- `queued`：本次还没有向会话发送，等待空闲。
- `dispatching` / `submitted`：已有或可能已有投递，重启后只读查询原生记录，不盲重发。
- `uncertain`：传输结果暂不明，只继续核实原生记录，不重新提交。
- `ready`：已经核实本次结果并持久化公开回复，等待发送。
- `sending`：回复已发起；若崩溃或超时，转为 `held`，不盲目重发。
- `held`：需要核对的歧义、混入私人输入、上下文权限不足或回复格式问题。后续任务暂留队列，保留顺序。
- `sent`：机器人回复已拿到消息编号。
- `failed`：已核实原生任务失败，没有自动发送猜测的结果。

发送使用不超过 50 字符的固定幂等键。但远端幂等有效期和网络结果不可完全依赖，因此即使有幂等键，未知发送结果仍不会自动重试。处理 `held` 时应先核对原会话任务和飞书消息；这版没有一键重发或强制放行命令。

入站线程会在进入任务处理前将符合条件的消息写入 SQLite，忙碌中的 CLI 调用不会阻止新任务持久化。服务停机期间的未接收事件是否补发取决于飞书；本模块尚未实现离线消息回扫。保留已发送记录用于去重，长期运行需要按部署政策另行备份和清理。

```bash
python3 -m unittest discover -s integrations/feishu_project_bot -p 'test_*.py' -v
```
