# Harness 受控记忆与原生推理代次

日期：2026-11-11

状态：B2 已完成开发代码、本地合成模型和完整服务端回归范围的阶段验收，尚未启用到共享服务。B1 上下文统计已通过本地开发验收；本设计在用户持续开发授权下实施。证据见 [受控记忆验收](../evidence/HARNESS_MEMORY_2026-11-11.md)。这不代表真实供应商记忆质量、客户数据、生产部署或整个产品已经验收。

## 1. 目标与不做的事

沿用知行工作台已有的 `NativeMemory`，让 Harness 能在当前用户、当前会话的授权范围内列出、读取和申请写入 Markdown 记忆。写入必须经完整内容人工审批，并在本轮成功结束后才生效。

必须解决两个不同问题：

1. 修改存储中的记忆后，旧原生会话中已经出现的记忆、工具结果和助手复述仍可能存在；不能用一句“请忘记”代替隔离。
2. 文件写入与 SQLite 更新不是同一个事务；不能出现“文件已经改好，但原生会话仍按旧代次恢复”的部分成功。

本轮不做跨会话共享记忆、自动总结、上下文压缩、批量记忆规划、模型代审写入、任意文件系统工具或历史答案自动重放。不修改旧 Claude 会话的原生记忆协议和恢复行为。不得把本设计解释为撤回供应商已经收到的信息，或删除应用中的历史聊天与审计。

## 2. 当前实现与复用边界

以下是代码现状，不是 B2 已完成的能力：

| 现有入口 | 继续复用的合同 | B2 必须补的部分 |
| --- | --- | --- |
| `server/app/memory.py` 的 `NativeMemory.authorize/root/revision/view/read/edit` | 用户拥有会话；会话级逻辑目录；Markdown 相对路径；版本冲突；管理页读写与删除、清空接口 | Harness 存储后端选择、不可变快照、代次切换、严格文件描述符校验、写入生命周期 |
| `MAX_FILE/MAX_TOTAL/MAX_FILES` | 每文件 128 KiB、当前有效记忆总计 1 MiB、最多 100 个文件 | 按 UTF-8 实际字节计数；暂存与历史快照另设磁盘上限 |
| `conversation_memory_scopes` | 会话记忆的 revision、digest、origin | 当前快照指针及提交绑定，不能另建一套用户可见的记忆库 |
| `NativeMemory.initialize` | 新会话为空；旧共享目录仅作为一次性历史快照来源 | Harness 只读导入及原子登记；不得原地搬走、改写或清理旧目录 |
| `Service.runtime_config` | 用户启用、助手可用、资源权限和版本检查；记忆版本进入 fingerprint | 加入原生代次与有效快照绑定；不允许刷新摘要时静默接纳外部改文件 |
| `HarnessToolBridge.invoke` | 宿主授权、审批、操作前后复核；模型只提议动作 | 三种精确记忆工具和提交后结果事件；写入不走低风险模型代审 |
| `SessionActor` / `RunManager` | 串行会话执行、关闭 owned Node、终态与恢复 | 成功提交的原子边界，不能把已提交的记忆随后标成失败或取消 |
| `AttachmentPrompt` | 上传归属、内容摘要、历史收据、权限复核 | 历史收据按原生代次筛选，不再按整个应用会话无差别继承 |

当前 `NativeMemory.edit` 会在 SQLite 事务中执行文件替换/删除；SQL 回滚无法撤销文件系统变化。当前路径校验也不等同于逐级 `dirfd + O_NOFOLLOW` 的读写合同。这些都是实现 B2 时要解决的缺口，不能直接复用为“已经具备事务与 TOCTOU 防护”。

### 2.1 单一逻辑接口，而非平行系统

- `/conversations/{id}/memory`、`/memory/file` 继续是唯一的用户管理入口；相对路径、revision、容量含义不变。
- `NativeMemory` 根据会话执行器选择内部存储策略。Claude 继续现有目录策略；Harness 经同一服务对象解析当前快照。新工具也调用该对象，禁止绕过管理接口另维护一套内容。
- Harness 的 `root/read/file_index/digest` 等内部调用必须一致解析同一已提交快照；不能出现管理页看旧平面目录、工具读新快照的双真相。
- 当前快照只读，修改经专用发布方法；任何调用者都不得拿 `root()` 返回路径直接改文件。该路径不作为模型参数或工具结果返回。
- 原有 legacy 只读接口仍读取原件。本文不要求迁移 Claude 历史或更改其 `sdk_session_id`。

## 3. 授权、版本和工具合同

模型不得提供 `user_id`、`conversation_id`、原生 session ID、绝对路径、快照目录或目标代次；它们全部由宿主从本轮运行绑定。

每次工具调用绑定：用户 ID、应用会话 ID、run ID、原生代次、记忆 revision/digest、快照 ID、助手及工具授权版本。读取前和返回前，写入申请前、审批后及最终提交前，均复核当前授权。对模型工具与运行，取消、账号停用、助手撤权、会话归档、active run 不匹配或策略变更均默认拒绝。管理页面继续允许本人主动查看、编辑已归档会话的记忆，保留旧管理合同；这不允许模型重新执行归档会话。

| 工具 | 唯一输入 | 结果与权限 |
| --- | --- | --- |
| `memory_list` | 空对象 | 返回当前代次的相对 Markdown 路径、字节数、revision；不返回宿主路径。仅当前授权作用域可读 |
| `memory_read` | `path`、`expected_revision` | 返回指定文件的 UTF-8 正文、revision、内容摘要；版本变化则拒绝，不偷偷读新版本 |
| `memory_write` | `path`、完整 `content`、`expected_revision` | 仅申请一个文件的完整 upsert；人工允许后返回 `approved_pending_commit`，不返回“已保存” |

首个切片每轮最多一个待提交 upsert；第二个不同写申请明确拒绝。同一申请的重试按幂等结果处理。删除和清空仍由用户现有管理界面执行，不新增对应模型工具。

路径沿用最多五层、240 字符的相对 Markdown 名称限制，拒绝绝对路径、`..`、隐藏路径段、反斜线、控制字符、冒号和非 `.md` 后缀。文件数与总字节上限在合成完整候选快照后检查，不能只校验本次字符串长度。

### 3.1 人工审批的内容必须完整

- 审批页显示当前会话、相对路径、基准 revision、旧内容摘要、拟写入的**完整正文**和可选差异。完整正文不能被摘要或截断后的预览代替；大内容可折叠/滚动，但必须可完整查看。
- 以纯文本安全展示，不执行 Markdown 内 HTML、脚本或图片远程请求。普通日志与 SSE 不重复广播正文；正文只通过拥有该审批访问权的受保护接口提供。
- 审批对象绑定规范化 UTF-8 正文字节摘要、路径、用户、会话、run、代次、revision、审批策略版本及失效时间。批准之后修改任一字段都需要新审批。
- `memory_write` 至少需要人工明确允许，不能被助手的自动批准名单或模型代审变成自动写入。若已有高风险策略要求管理员/双人审批，只能增加限制，不能被 B2 降级。
- `memory_list/read` 也必须显式登记为受控会话记忆操作；不得通过伪装成通用 `Read`、工作区 scope 或另一个已允许工具来借用授权。
- 用户通过现有管理页主动保存/删除/清空，是用户自身的明确操作，不再要求模型审批；但同样执行版本 CAS、空闲检查与代次切换。

## 4. 写入时序：允许不等于已保存

推荐的宿主状态机：

```text
proposed -> awaiting_approval -> approved_pending_commit -> prepared -> committed
                     |                   |                  |
                     +-------------------+------------------+-> aborted
```

1. 宿主校验内容与容量，持久化申请摘要和私有候选内容，再请求人工审批。未经批准的数据永远不进入当前有效记忆。
2. 人工批准后，再核验授权、策略、run/代次和基准版本。记录 `approved_pending_commit`，工具返回“已批准，本轮成功结束后保存”。本轮读取仍看到旧快照；模型不能依靠刚申请的内容已生效。
3. 原生 `session/wait` 正常完成、附件等末尾复核通过且 owned Node 已关闭后，才允许进入提交准备。宿主必须保留本次独占的 `Popen` 对象并通过 `poll()` 确认其已退出，同时完成等待/回收；不能仅以 `client is None`、`close()` 已调用或 Python 等待任务已取消判断进程退出。进程身份丢失、退出未确认或关闭超时均不得发布。不能在 Node 仍可能继续推理时发布新记忆。
4. 保持会话的执行/变更闸门，准备并校验新快照。发布事务前再次复核账号、助手、审批、取消状态、权限版本、旧记忆版本和旧代次。
5. **同一 SQLite 提交**完成快照指针、revision/digest、原生代次、resume ID 清空、上下文缓存失效、申请终态及该 run 成功终态。此提交是唯一的成功线性化点。
6. 事务提交之后才发送 `memory.updated`/运行完成事件或 HTTP 成功响应。通知通过已提交事件重放，不以“通知发送成功”作为持久化成功条件。

若模型失败、流中断、用户拒绝、超时、取消、授权/审批变化、内容或 CAS 不匹配、关闭 Node 未确认成功，申请终止，不改变有效记忆。临时目录清理失败不意味着申请成功。

运行最终收尾中凡是可能导致失败的验证，必须排在提交事务之前；不能先提交记忆，再因为非必要的导出/通知异常把运行改成失败。提交成功后的取消返回“已完成，未撤回已提交操作”，不能伪装成取消成功。实现时需调整现有 actor 的 `finally/finish` 调用顺序，而不是在其外侧再补一个写文件回调。

## 5. 编辑、删除、清空后的原生代次

应用会话 ID 与原生推理代次是两个概念。建议在会话作用域增加宿主持有的单调 `native_epoch`，并保留受保护的代次审计记录；字段名在实现时统一确定。

- 记忆实际新增、编辑、删除及用户明确清空操作，都使下一轮采用新的 Harness 原生 session ID。清空已经为空的记忆也切换代次，避免旧历史中仍有此前暴露的信息；可复用相同空快照，不必复制文件。
- 记忆 `revision` 仍描述有效内容版本，仅在内容摘要变化时增加；`native_epoch` 描述推理历史隔离。因此空记忆再次清空可保持 revision、增加 epoch，两个值必须独立绑定，不能用 revision 代替代次。
- 完全相同内容的普通 upsert 可返回 `unchanged`，不增加 revision、快照或代次；必须先完成版本与权限核验，不得把内容相同用作绕过审批的理由。
- 原生代次切换与新记忆快照发布一起提交，不能只改 `fingerprint` 然后仍 `resume_session(old_id)`。
- 下一代只收到当前新用户输入、当轮明确选择的附件、当前系统/助手配置和当前授权工具结果。不得从应用历史自动拼装旧用户消息、旧记忆、总结、摘要、工具输出或助手答案。
- 旧应用聊天、文件引用、审批和运行审计保留，可按原有授权查看；它们不再成为新代原生模型的隐式输入。界面明确提示“记忆已更新，后续推理使用新上下文；历史聊天仍保留”。
- B2 不顺便开放自动记忆全文注入。模型通过 `memory_list/read` 获取当前版本内容；记忆内容作为不可信业务资料，不能覆盖系统指令或扩大工具权限。
- 不声称删除了供应商已接收数据，不声称完成物理擦除，也不把保留的应用历史当作“仍在模型上下文中”。

### 5.1 附件收据随代次

当前 `AttachmentPrompt` 查找整个会话的 `harness_attachments` 收据。B2 必须在 run 元数据记录宿主代次，且复核**当前原生代次的全部 admission 尝试收据**，不能仅筛选成功 run。RPC 返回失败、超时或取消时，Node 仍可能已经持久化输入；宿主不能据此证明附件未进入原生历史。

- 同代恢复继续检查已有附件的归属、删除状态、绑定摘要、实际字节和原有限额；不能因 B2 放松检查。
- admission 尝试收据必须在提交输入给 Node 之前持久化，并绑定当时代次；失败、取消、连接断开及结果未知的 run 收据仍计入同代检查和限额。无法证明没有入库时保守保留，不能在错误清理中删除。尚未发出 RPC 但已有收据也可保守纳入，不推断上游未持久化。
- 换代后，不再重放旧附件，也不让已删除的旧代附件永久阻塞不继承它的新代。
- 用户在新代显式再次选择旧文件时，按当前权限重新验证并生成新代收据；旧收据不能充当授权。
- 缺少代次的旧收据只允许在经过明确登记的 legacy 代次中使用；不得把“缺字段”默认解释成任意当前代次。迁移不清除旧审计。

## 6. ADR：以不可变快照和原子指针避免部分成功

**决定状态：建议采用，尚待实现与故障注入验收。**

SQLite 无法回滚原地 `replace/unlink`。因此不采用“先改现有文件，再更新 revision/epoch，出错时尽量改回”的方案；同样不依赖提示词忘记旧记忆，也不通过复制整个原生会话来切换代次。

### 6.1 建议存储布局与权威来源

继续使用 `NativeMemory` 的逻辑作用域，以服务端生成的 ID 存放内部快照，例如：

```text
<data_dir>/conversation-memory-snapshots/<user_id>/<conversation_id>/<snapshot_id>/
<data_dir>/conversation-memory-staging/<user_id>/<conversation_id>/<operation_id>/
```

路径不是外部 API，不授予模型读写能力。数据库中的有效快照指针是唯一权威；磁盘上存在目录不代表已发布。快照清单绑定用户、会话、文件相对路径、字节数及摘要；清单与树摘要须由宿主数据库绑定，不能信任目录自己声称的身份。

建议扩展 `conversation_memory_scopes` 保存 `active_snapshot_id`，扩展会话执行信息保存 `native_epoch`，以一张宿主变更账本保存幂等键、预期版本/代次、内容摘要、审批绑定、状态和最终结果。该账本管理同一份 NativeMemory 的事务，不是另建记忆产品。

### 6.2 原子发布步骤

1. 用短 SQLite 事务预留该会话的唯一变更闸门和配额；绑定当前 revision/epoch。闸门需跨进程可见，不仅是 `asyncio.Lock` 或单进程 `db.lock`。聊天提交、上下文恢复和其他记忆编辑都检查它。
2. 在全局 DB 锁外，由已验证旧快照生成完整新快照；首切片最多 1 MiB。写入私有临时目录，核验每个文件及清单，逐文件 `fsync`，再同步目录；发布到全新最终目录，并同步父目录。不得覆盖现有快照 ID。
3. 取得事务后，检查闸门持有者、当前用户/会话/助手/审批、run 成功候选状态、无取消、revision/epoch CAS、快照 ID/摘要及配额；不匹配则回滚并终止。大小受限的最终校验必须结合保持打开的目录描述符和 inode 身份，不能再次随意按路径信任目录。
4. 单次事务更新当前快照指针、记忆 revision/digest、代次、`harness_session_id=NULL`、`context_usage=NULL`、幂等账本、必要事件及运行终态，并释放闸门。不得中途单独提交某个字段。
5. 提交成功即可重放同一结果；提交失败时旧指针和旧代次保持不变。磁盘上未被引用的新目录只是孤儿，不可被 `root/read/runtime_config` 自动采用。

SQLite 与文件系统必须使用能支持上述同步语义的本地数据盘；实现需核验 SQLite 同步设置和文件/目录 `fsync`，不能把“进程崩溃测试通过”表述为任意掉电/硬件故障保证。文件同步发生在 SQLite 指针提交前；若重启后已提交指针引用的树缺失或损坏，默认阻断该会话，不回退到旧原生历史继续推理。

### 6.3 崩溃与失败矩阵

| 故障位置 | 重启可见状态 | 保守处理 |
| --- | --- | --- |
| 未批准或批准后，本轮未完成 | 旧快照、旧代次；申请未提交 | 原运行按现有规则中断，申请 `aborted`；不自动重新调用模型或补写 |
| 新树写到一半 | 旧指针，私有暂存树 | 解除确认失效的闸门；清理只属于本申请的孤儿 |
| 新树已 fsync/发布，SQL 尚未提交 | 旧指针，完整但未引用的新树 | 不采用新树；终止申请并延后清理孤儿 |
| SQL 事务执行中 | SQLite 恢复到提交前或提交后的一致状态 | 按账本和指针判定，不靠 HTTP 是否送达猜测 |
| SQL 已提交，HTTP/SSE 未送达 | 新快照、新代次、成功终态及结果均在 | 同一幂等请求返回已提交结果；事件重放，不再次写入或再增加代次 |
| SQL 提交后磁盘缺失/损坏 | 指针存在但完整性校验失败 | 明确恢复错误，禁止模型启动；不得拼接旧树或沿用旧 session |
| Node 关闭失败、权限变化或取消先发生 | 无发布提交 | 不变更有效记忆；不报告“已保存” |

**禁止的部分成功状态**：仅写入文件、仅增加 revision、仅清空 resume ID、仅把运行标成功、或先发成功事件再提交。若实现无法让以上数据库状态同一事务提交，B2 写入不得开放。

### 6.4 幂等与并发

- 模型申请使用宿主生成的 operation ID，绑定 run、tool call、用户、会话、代次和规范请求摘要。相同 key/相同摘要返回原状态；相同 key/不同正文、路径或版本拒绝。
- 管理界面为 Harness 修改携带稳定的幂等键，断线后先查询/重试同一操作，不重新生成 key 重复写入。旧 Claude API 兼容不变。
- 已提交结果的重读仍检查调用方权限；幂等键不是授权令牌。过期审批不能在新 run、新代次或新版本复用。
- 取消与提交竞争以同一数据库事务顺序判定：取消先持久化则不能提交；提交先完成则返回已完成。审计分别记录批准时间、提交时间、取消未生效原因。
- 进程启动先恢复账本/闸门，再开放会话运行；不得在 `RunManager.recover` 将未提交运行标中断之后，另一个回调仍补写记忆。

## 7. 迁移、文件安全与磁盘边界

### 7.1 旧目录只读导入

首次启用 Harness 快照策略时，仅在会话空闲且持有迁移闸门时，由 `NativeMemory` 对当前会话目录做有界、只读快照。保持原目录和 legacy 源目录不变；导入来源与原 digest 写入审计。

复制前后核验源 inode、mtime/ctime、大小和内容摘要；变化则终止重试，不悄悄接纳。新树完整同步后，原子登记快照指针与迁移标记。崩溃留下的目录不能被自动识别为“迁移成功”。未出现有效记忆变化时可保留逻辑 revision；首次接入 B2 对已有 Harness 会话执行一次明确的新代次切换，避免无法证明旧原生历史中有哪些记忆。空新会话直接登记空快照/初始代次。

旧 Claude 会话仍走旧目录与原恢复 ID。不得把修改 `NativeMemory.root` 的全局行为当成所有执行器都已迁移；须有按会话执行器/存储版本的显式分支和兼容测试。

### 7.2 文件描述符与篡改边界

- 私有目录 0700，文件 0600，验证当前服务 UID；逐级打开目录及文件使用 `dirfd`、`O_NOFOLLOW`，只接受目录或常规文件，拒绝软链接、硬链接（文件 `nlink != 1`）、FIFO、设备和 socket。
- 有界读取前后校验 inode、设备号、大小、mtime/ctime；验证结束后原子复核数据库指针和授权。不能用 `resolve()` 加随后 `read_bytes()` 代替这些检查。
- 按实际 UTF-8 字节验证编码、文件数、文件/总容量；解析清单拒绝重复路径、额外未知路径和不规范相对名。目录深度仍有限，摘要遍历不能进入旧原生 session 或任意工作区。
- 复制与哈希放在全局 DB 锁外，通过会话闸门及 CAS 衔接；避免最多 1 MiB 的文件 IO 长时间阻塞其他用户的取消与审批。
- 运行绑定快照不可由模型、文件工具或记忆管理页原地修改。检测到宿主外部改写已发布树，报完整性错误，不通过现有自动 `refresh` 把篡改升级成合法新 revision。
- 同 UID 恶意宿主进程、管理员改数据库或内核/磁盘故障不属于工具沙箱能消除的威胁；不能将上述应用边界声称为 OS 隔离。

### 7.3 有界保留和清理默认

建议首切片采用以下保守工程默认，均为拟实施配置而非当前能力：

| 项目 | 默认 |
| --- | --- |
| 当前有效记忆 | 沿用每文件 128 KiB、总计 1 MiB、100 文件 |
| 一个会话并行修改 | 1 个；每轮最多 1 个待提交 upsert |
| 暂存预算 | 每会话最多 2 MiB，包含候选内容与构建树；单份清单最多 64 KiB，计入项目总预算 |
| 已发布快照保留 | 每会话最多 32 个不同内容快照、合计 32 MiB；代次无内容变化可复用快照 |
| 项目模块总预算 | 256 MiB，包含已发布快照、暂存、孤儿和清单；只统计本模块拥有的目录 |
| 剩余磁盘保护 | 可用空间不足 1 GiB 时拒绝新变更，不影响现有记忆读取 |
| 未提交孤儿清理 | 确认申请终止、无引用/无活跃持有者且至少 24 小时后，才可清理 |

普通聊天、列表、读取、上下文统计与内容不变的写入不复制快照，不能每轮无限复制。配额以宿主持久化预留跨进程执行；首次保存审批候选内容之前即预留空间，构建时再预留新增树空间，不靠提交后才扫描发现超限。清理失败的孤儿仍占配额，不能从账本扣掉却留在磁盘上无限积累。

首切片**不自动删除已发布历史快照**。到达配额明确拒绝并给出维护提示；不得为“自动腾空间”删除旧聊天、审批正文、原生历史、legacy 源文件、仍被历史记录引用的快照或其他项目目录。已发布快照未来的保留策略/人工清理需独立确认，本轮不默认获得该授权。

孤儿 GC 必须先查账本与全部引用，验证模块拥有的目录 ID、owner、类型和 inode，在闸门保护下仅删除对应暂存/孤儿树。出现软硬链接、目录替换、未知文件或权限异常则停止并报告，不使用跨目录递归跟随删除。清理失败记录为待维护，不更改提交结果，也不重试写入。

用户“清空记忆”表示当前有效记忆为空、下一代不自动继承旧内容；它不是对历史聊天、审批记录、备份或供应商数据的安全擦除承诺。界面必须在操作时说明此边界。

## 8. 计划变更面与实现顺序

本节为实现顺序；用户已授权持续开发。每个切片仍须完成测试与安全复核，不扩大到生产部署或共享服务重启。

1. `db.py` 与 `memory.py`：账本、闸门、快照指针/代次，统一 NativeMemory 内部策略，先完成手动编辑/删除/清空与崩溃恢复合同。
2. 宿主专用记忆工具模块、`harness_tools.py`、`service.py`、安全/审批登记：三种工具及精确作用域，写入完整内容人工审批，默认拒绝。必要的 UI 完整内容视图不能省略。
3. `runtime.py`、`harness_runtime.py`：成功后提交与原子终态，冷启动选择新代次，context binding 纳入代次。不得在工具 handler 中直接改当前文件。
4. `harness_attachments.py`：记录并过滤代次收据，保留同代撤权检查。
5. `server/harness/profile.py`、`workspace_plugin.ts`：只增加三个宿主分派名称/描述，不加载 native fs、shell、记忆文件插件或任意读取能力。
6. 前端管理/审批提示、测试及交付文档：显示待提交、已提交、失败/取消、新上下文边界；不能仅看模型自然语言宣告成功。

先用离线合同验证，再使用固定官方 Harness + 私有 Node + loopback 合成模型进行端到端请求检查。所有临时目录与缓存位于数据盘，不需要真实客户数据或外部/付费模型。真实供应商记忆效果评测属于之后独立验收，不借本切片暗中调用。

## 10. 待落实风险与后续决定

- **事务接线是交付阻塞**：当前 actor `finally`、`RunManager.finish` 和 NativeMemory 文件编辑尚未实现上述单一提交边界。必须经故障注入证明，再开放模型写工具；不能先做 UI 后宣称成功。
- **迁移与兼容是交付阻塞**：必须证明所有 Harness 记忆读取走同一指针、首次导入不改原件，Claude 行为不变；不能只改工具路径而遗漏管理页或自动 revision 刷新。
- **审批 UI 是交付阻塞**：现有通用参数展示能否完整承载 128 KiB 正文，需要实现时核验；若不能安全展示完整内容，本轮应拒绝该写申请，而不是截断后让用户批准。
- **保留配额是保守默认**：32 个/32 MiB 会话快照、256 MiB 项目预算及 1 GiB 余量可按明确的本地容量测试调整。不得为了达到写入指标偷偷启用历史删除；已发布历史的删除/备份保留另行决定。
- **隔离语义需明确展示**：换代保留 UI 历史但不自动携带旧对话，会降低旧上下文连续性；这是防止旧记忆继续影响推理的有意取舍，不是悄悄丢失聊天记录。
- **执行阶段再取证**：本文件仅静态设计，无测试通过、无真实模型效果、无共享服务更新。B1 通过后按上述顺序逐项实施和验收。

## 10. 实施时明确的支持边界

- 运行管理器仍是单应用进程模型：审批等待和运行所有权在本进程内管理。禁止启动第二个完整应用实例连接同一正在执行任务的数据库；启动恢复会把旧非终态任务标为中断。跨进程记忆闸门和事务竞争测试不等于全站多工作进程无损运行验收。
- 手工操作的浏览器恢复记录只保存会话、操作编号、种类、路径和预期版本，不缓存正文。刷新后先查询同一操作；未找到记录不表示请求永远不会到达，不能自动生成新编号重试。丢失的写入草稿须重新填写，服务端以原编号和规范请求摘要判断是否同一请求。
- 记忆配额包含快照、孤儿、候选正文及数据库序列化副本的保守预留，但这是记忆模块逻辑预算，不是整个 SQLite 文件、日志文件或磁盘的物理硬上限。不自动删除已发布历史。
- 高风险双人审批策略启用时，本切片拒绝私有记忆写入，不把管理员身份当作读取他人完整记忆的权限，也不降级成单人审批。将来若需要多人审阅私有正文，必须增加独立授权范围与撤销测试。
