# 飞书 CLI、邓凯文-bot 与大管家身份边界

## 结论

飞书 CLI 和邓凯文-bot 不是同一个运行进程，也不承担同一种职责。

- `feishu-doc` 是“用户身份”的命令行工具，当前命令包括 `login`、`whoami`、文档读写、云空间和原始 OpenAPI 调用。它通过 OAuth 保存用户 `access_token`/`refresh_token`，不会接收飞书机器人事件，也不会启动 WebSocket 消费者。
- 邓凯文大管家是飞书企业自建应用里的机器人入口。学校云上的 steward 使用应用凭据建立 WSS 长连接，接收 `im.message.receive_v1`，再调用 Claude CLI 并通过机器人消息接口回复。

当前学校云的历史配置让两者共享了同一个应用注册和 token 文件路径 `/home/dengkw/.config/feishu-doc/token.json`：steward 读取其中的 `app_id`、`app_secret` 和 `user.open_id`，但不使用 CLI 的用户 `access_token`/`refresh_token` 来接收机器人消息。共享应用可以工作，但会把文档 CLI 的权限、机器人事件订阅和密钥轮换耦合在一起。

## 推荐配置

建议把机器人、网页工作台和用户 OAuth 分成独立的企业自建应用：

1. **邓凯文大管家**：开启机器人能力和长连接事件订阅，订阅 `im.message.receive_v1`，只配置消息接收、回复所需权限；应用凭据放在学校云 steward 的独立 owner-only 文件中。
2. **飞书 CLI**：保留用户 OAuth，用于文档、云空间、知识库等操作；凭据保存在使用 CLI 的那台机器上，不作为 steward 的 WSS 凭据。
3. **知行工作台**：只开启网页应用能力，承载完整的 H5 工作台和网页免登；不订阅机器人事件，也不承担大管家消息桥接。

飞书 CLI 不需要机器人能力，除非后续明确要让 CLI 代替用户发送 IM 消息。大管家必须是机器人应用，因为它要接收用户发给 bot 的事件并主动回复。

## 截图对应的问题

截图中的“Claude 管家”是飞书应用的显示名称；它来自飞书开发者后台的 bot 名称，不能靠 Claude CLI 自动改变。产品命名确定后，应在大管家应用的机器人配置中改成“邓凯文大管家”并重新发布。

截图中的“上次任务结果未确认”是 steward 的保护状态。旧逻辑会在这个状态下直接拦截普通消息，导致“你是谁”也收不到 Claude 回复。当前线上 `all-messages-20261107-154500` 已改为：除 `/status` 和 `/recover` 这类明确的 steward 控制命令外，所有用户消息都进入学校云 Claude；prompt 会提醒 Claude 只处理本轮消息，不重放上一轮未确认操作，也不会自动清除 blocked 标记。

## 迁移边界

拆分应用时先保留旧应用和旧 steward 的回滚文件，完成以下顺序后再切换：创建大管家应用、发布机器人、配置独立凭据、确认 WSS 单实例、发送一条低风险私聊、再停用旧应用的机器人事件订阅。不要在两套应用上同时消费同一个生产会话。
