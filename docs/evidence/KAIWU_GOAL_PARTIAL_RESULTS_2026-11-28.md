# 委派两项后，从父会话取回第一份成果

普通成员从首页按名称选回原父会话后，可以在“持续目标第 1 轮”下看见每一项的主题、状态和已经返回的原答。第一项由子任务独立作答，第二项失败时，已经交付的结果仍留在原会话。

## 用户怎么操作

从隔离工作台首页以普通成员身份登录，新建会话，在持续目标窗口写下“请并行委派两个独立任务，分别检查订单导出的日期范围和发票预览的格式；每项给一句核对建议，不读写文件。最后逐项说清哪项完成、哪项没有结果。”用户创建目标、授权、点“开始一轮”。固定 Harness 的父模型调用一次 `delegate_tasks`，实际启动两个独立子任务。用两份合成应答控制完成先后，第二项收到请求后等待，完成回访后才让它返回 HTTP 400。原有启动、全成功和全取消验收见[联合证据](KAIWU_GOAL_TEAM_JOINT_2026-11-27.md)。

## 父回答与实际交付

正常父答样本中的真实工具回报含第一项完整原答，第二项为 `failed / executor_error`。合成父模型根据该工具回报生成汇总，明确写出发票核对失败。每场共 5 次本机模型收件，包括 1 次会话引导和本轮 4 次（父派工、两个子任务、父汇总）。两次回访的模型收件累计分别为 4→4、5→5，产品 POST（提交）均未增加。每次均关闭整棵 Chromium 进程树，再用同一普通成员的浏览器资料回访。

另用一个刻意与工具回报矛盾的合成父模型。相同一成一败回报下，它在父答里声称“两项核对都已完成。”该次父答为实录，不作为两项成功的证明。开发版在这条父答正文下单独显示“子任务回执 · 1/2 项完成 · 1 项失败”。直接展开回执和相应子项，即可读到订单原答、看到发票失败。误报文字仍保留。两次展开新增提交 0 次、模型请求 0 次。对同一旧库的三条父答逐条检查：混合轮显示 1 份、随后无委派的普通回答 0 份、另一会话的全成功轮 0 份。用普通成员真实历史的 40 条消息窗口再验，页首只有父答时单独读取该轮 1 次；同页已有原提问时复用它的读取，34 条普通历史行未新增计划查询。
