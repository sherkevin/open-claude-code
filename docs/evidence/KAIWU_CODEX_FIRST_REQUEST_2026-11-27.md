# 从第一条工程请求到真实输出

用户在业务会话工具栏打开「Codex 工程任务」，直接输入并发送。开物先显示本地提交反馈，再通过本人状态接口确认宿主已收到请求。已写入的原生会话编号、已获准的执行轮次和模型实际输出分别有回执。整页刷新只读取进度。原有手动准备、取消和中断核对入口仍可用。

### 同机实测

使用固定 Codex 0.165.0、实际 Chromium、私有 HOME 和空工作区。任务为“请用一句话说明 pwd 命令的作用，不要执行命令或修改文件。” 隔离 HTTP 提供方立即返回相同短句。每个开物样本均核对 1 个线程、1 轮和 1 次模型收件，工作区前后为空。单跑和并发各取 2 个首次请求样本。四组并发沿用 Goal/Team、子任务取消和 Mem0 三项伴随工作；样本共享宿主的操作系统缓存。

首文样本中位数由单跑 11.902 秒降至 4.453 秒，四组并发由 13.874 秒降至 8.141 秒。原来准备一次、关闭进程、发送时再校验并启动第二个进程并恢复线程。旧版一个单跑的首进程关闭耗时 4.274 秒，两次并发均约 4.626 秒。新版在同一进程中建好线程并提交首轮。本地忙态的毫秒读数只反映控件响应。页面的宿主确认来自实际请求持有的所有者锁，首段来自与轮次编号相符的原生增量或最终正文。快速掠过的原生阶段可能落在两次页面查询之间。

### 刷新与反例

旧版有 1 次在准备开始后 250 毫秒整页刷新，回到“尚未准备会话”，30 秒检查失败。手动更新后原绑定可见。新版另 1 次在发送后 250 毫秒整页刷新并重开，0.888 秒看到宿主已确认原请求，5.767 秒看到首文，未自动重发。早期候选 c69df32 的并发检查还抓到同号已完成正文重复显示两次。最终版在执行器清理期间也优先显示该轮已保存的结果。

旧 d604e89 在四组负载下曾从加锁到落盘用时 31.504 秒，超过 30 秒检查窗。模型当时收到 0 次请求；同版单跑准备响应 9.430 秒。这个失败保留在记录中。当前计时按用户可用、绑定落盘和 POST 返回分别记，不能用一次快速确认替代“会话可用”。新旧负载同时启动；旧版两组的首文分别晚于首个伴随作业结束 3.719 秒、3.022 秒，新版两组首文均在四项共同运行期间到达。

### 原生对照

以下均从启动独立 CLI 进程计时，读到 stdout 的实际通知和首句正文。会话通知表示已取得编号。另用新进程重开同一编号，并在提供方请求中核实原对话内容，此步骤验证持久恢复。开物页面的宿主接单时间与原生执行通知语义不同。样本量不足以估计尾延迟或说明并发加速。

| 入口 | 负载 | 样本数 | 会话编号通知中位数 | 执行通知中位数 | 首文中位数 |
|---|---|---:|---:|---:|---:|
| Codex exec | 单跑 | 2 | 2.298 秒 | 2.810 秒 | 2.840 秒 |
| Codex exec | 四组并发 | 2 | 1.752 秒 | 2.090 秒 | 2.121 秒 |
| DeepSeek Harness headless，关闭自动拟题 | 单跑 | 2 | 3.598 秒 | 3.601 秒 | 4.168 秒 |
| DeepSeek Harness headless，关闭自动拟题 | 四组并发 | 2 | 3.910 秒 | 3.912 秒 | 4.974 秒 |

默认 Harness 发出 2 次 HTTP，CLI 正常完成并保存会话标题；按 1 次 HTTP 设计的匹配检查退出 1。这次测量单独保留。关闭自动拟题后，每个样本与 Codex 一样只有 1 次模型请求。原生两端各在 2 次新进程重开中恢复旧历史，重开首文中位数分别为 Codex 0.250 秒、Harness 3.277 秒。登录、网络服务时间、模型真实生成速度，以及浏览器和 CLI 使用不同展示层的耗时，均不在本次实测的归因范围内。

按相同的 2 个样本取中位数，开物首文仍比原生 Codex 单跑晚 1.613 秒、并发晚 6.020 秒。校验固定二进制、初始化、持久保存及页面读回都可单独观察。本组样本不能把全部差额归到任一环节。

### 原 30 秒门槛和后续回执

以原 d604e89 提交、与当时相同的静态资源 SHA-256、原脚本和原四组负载另跑 1 次，准备响应 11.062 秒，4 个退出码为 0。刷新后能取消原第二轮，整个样本共 2 次模型收件。历史超时在这批没有重现。性能候选 4579480 的手动入口也按相同门槛保留对照：单跑与四组并发各 1 次，持久绑定分别用 3.276、5.000 秒，浏览器可发送分别用 8.020、8.896 秒。样本没有覆盖生产机器和真实模型延迟。

E2.3 接着验了旧请求回执。A 的最终 HTTP 响应丢失、另一标签页的 B 已完成时，原页面刷新只显示 B。开发版增加本人按请求编号的只读查询。同一用户的 A 标签页刷新后可分别看到 A 的留存结果和最新 B，找回过程 2 次 GET、0 次 POST。累计完成 9 轮后，A 已超出最近 8 份回执留存范围，页面显示曾获准、正文无法找回，另起新任务需用户显式提交。完整页面刷新不会自动提交。浏览器禁止访问会话存储时，当前页仍能显式用原编号重试。此专项使用真实 Chromium、3 个标签页及合成 stdio 对端，11 个合成轮次，页面错误 0 个。普通业务消息历史尚未纳入，工程结果仍由「Codex 工程任务」查看。

后续回执版本 39269e8 的真实 Codex 路径又单独复跑，单跑与四组并发各 1 次，页面宿主确认 0.324、0.322 秒，首文 5.842、7.668 秒。每个样本 1 次原生执行、1 次模型收件。主性能表按先固定的 4579480 归档。

VIP 原始证据根目录是 `/media/data3/dengkw/acceptance/kaiwu-l3-codex-browser-20261127/first-request-20261127/`。`controller/latency.json` 对应四组主表，`browser-comparisons.json`、各样本的 `timeline.json` 与 `codex/{browser,native}.jsonl` 可还原原始点击和实际执行时间。`native/summary.json`、`native/protocol.md` 保存原生进程及重开证据。`d604e89-historical/` 保留旧版精确复跑，`controller/next-history/` 保存丢回执和超出留存范围的前后对照。
