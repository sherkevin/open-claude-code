## 讨论中可以直接落为需求的内容

1. **助手是业务级入口。** 一个助手可以打开多个独立会话，直接与人对话，并组合工作流、工作方法、知识库、模型上下文协议连接、记忆、权限和安全策略。
2. **低代码平台面向客户。** 客户应能用预设能力加自定义能力，构造自己的助手，而不是只能使用研发预先写死的单一问答助手。
3. **工作流是一级可组合能力。** 工作流由人按业务流程构造，流程中可以放置智能体节点；工作流与工作方法、知识库、模型上下文协议连接、记忆和权限共同组成助手。
4. **能力要有池化和预设。** 用户可以创建原子能力，也可以从常见模板开始。讨论中给出的示例是财务申请、财务报销、填报表工作方法及相应工作流。
5. **工作流需要可视化。** 低代码体验不能只靠 JSON 或提示词；至少要有节点、连线、参数、输入输出、版本、测试和发布状态的可视化界面。
6. **需要区分对象层级。** 当前讨论把“助手”称为业务级智能体，把工作流中的“智能体”称为执行节点；这不是再增加一个八层安全层，而是跨八层的组合与编排平面。

## 讨论中仍需按产品基线处理的歧义

- **工作流是人手工构建还是由模型生成：** 录音先提出“让智能体搭工作流”的可能性，随后明确“工作流只能人来构造”。一期按人工可视化构建为基线；模型辅助生成留作后续实验能力，不能作为一期验收前提。
- **助手与智能体命名：** 为避免页面和接口混淆，一期将“助手”定义为面向业务的顶层 Agent，将“Agent 节点”定义为工作流内的受控执行节点；现有 `Assistant` 对象沿用，新增工作流节点类型，不把现有 `Sub-agent` 合成执行器冒充客户可见 Agent。
- **能力由助手自动挑选还是用户挑选：** 一期采用用户显式组合、服务端权限复核；可以提供推荐，但不能未经确认自动绑定工具、知识库或写入能力。
- **工作流是否直接等同于 Skill：** 不等同。Skill 是文本和参考资料组成的工作方法；Workflow 是有节点、数据流、条件和审批边界的可执行图。

## 与当前项目的差距

- 已有：助手、多个 Session、Skill、知识库与检索增强生成、模型上下文协议连接、记忆、权限、护栏、模型路由、审批和本地 Sub-agent 隔离。
- 部分补齐：服务端已增加 Workflow 资源、节点类型与数据契约、草稿/发布/回滚版本、版本哈希、无副作用合成回放和财务申请/报销模板；助手详情已增加本地低代码画布、节点配置、连线面板和模板入口；仍缺运行图投影、工作流级真实权限绑定、真实产物执行和客户可用的完整构建入口。
- 现有 `Sub-agent` 只完成本地合成安全骨架；它不能直接被宣传为工作流节点的真实生产执行器，工作流中的 Agent 节点目前也只允许 synthetic 模式。
