### 2.2 失败详情与复现

三个失败同属一个参数化用例 `tests/test_model_catalog.py::test_sdk_receives_selection_and_all_model_aliases`，参数分别为 `[light-low]`、`[high-high]`、`[max-max]`。异常相同：

```
app/security.py: AppError: (409, 'MODEL_SELECTION_REQUIRED', '模型服务配置已变化，请重新选择模型后继续')
```

调用栈（三者一致）：

```
tests/test_model_catalog.py:144: in scenario
    runtime = SDKRuntime(service, cid, service.runtime_config(cid), None, None)
app/service.py:494: in runtime_config
    provider_env = self.validated_provider(selection)
app/service.py:110: in validated_provider
    raise AppError(409, "MODEL_SELECTION_REQUIRED", ...)
```

用例逻辑（`server/tests/test_model_catalog.py:140-152`）：先 `patch_conversation` 设置推理级别，再把 `service.settings.provider_env` 替换成一组“旧”值（`old-key` / `old-model` / `old-small-model`），随后构造 `SDKRuntime` 并期望拿到 `${selection.upstream_model}` 与对应 effort。而会话的 `selection.provider_fingerprint` 是在替换之前按目录配置固化的；`validated_provider()` 用替换后的环境重新计算指纹，二者不一致即返回 409。换言之：**该用例的“替换 provider 环境”与“会话必须重新选择模型”的指纹校验语义直接冲突**，是当前源码上稳定存在的真实失败，不是环境或缓存问题。

复跑确认（只跑该模块）：

```bash
../.venv/bin/python -m pytest tests/test_model_catalog.py -q --basetemp=../.runtime/l3-baseline-server-rerun -p no:cacheprovider
```

- 退出码：**1**
- 结果：**3 failed, 19 passed, 1 warning in 4.79s**（18:22:27）
- 与全量运行完全一致，失败可稳定复现（非偶发）。

判断归属需要 L2 决策（本 L3 未修改任何源码）：要么用例应在替换环境后重新固化 `provider_fingerprint`（测试滞后于新校验逻辑），要么 `runtime_config` 应采用会话已记录的 provider 快照而不是现算指纹（代码行为与设计不符）。`docs/API_CONTRACT.md:75` 与 `docs/OPERATIONS.md:33` 明确“全局或单模型 provider 配置变更后，旧会话返回 409 `MODEL_SELECTION_REQUIRED`”；若以该设计为准，则问题更可能在用例一侧，即替换环境后未重新固化指纹。
