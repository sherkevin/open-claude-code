# DeepSeek Harness Foundation Implementation Plan

**Goal:** 在不替换现有对话服务、不丢失既有功能的前提下，建立可测试的开源运行时接入基础。

**Architecture:** 保留 `SDKRuntime` 默认入口；业务工具只维护一份实现，旧框架继续通过包装器调用。第一阶段只提供进程内、默认关闭的知识工具桥接器，尚不暴露网络端点，不启动 Harness。官方 Python 客户端使用模拟运行时验证协议，不把模拟结果称为模型端到端验证。

**Tech Stack:** Python、pytest、现有知识库和审批服务、固定版本 DeepSeek Harness Python SDK。

## 选择与边界

- 不直接替换：官方默认配置含 Shell，审批请求缺工具参数，取消、实时增量输出和上下文统计仍有契约缺口。
- 不复制知识库服务：避免两个运行时的权限、来源和文档版本行为分叉。
- 采用渐进桥接：业务工具独立于框架；后续通过经过审核的固定插件连接到这个入口。
- 不重启、不部署、不调用付费模型、不读取真实客户数据；临时目录、源码和缓存全部放在数据盘。

## 任务 1：框架无关工具注册表

文件：`server/app/workspace_tools.py`、`server/app/capabilities.py`、`server/tests/test_workspace_tools.py`。

1. 补注册表的契约测试：名称、说明、参数、读写注解、异常格式、来源和权限。
2. 原样迁移工具实现，保留旧 SDK 的审批回调语义，不将 `check_tool=False` 错当成已审批后的硬拒绝。
3. 运行新测试和原 `test_capabilities_04.py`，确认原有功能不变。

## 任务 2：默认关闭的只读知识桥接器

文件：`server/app/harness_bridge.py`、`server/tests/test_harness_bridge.py`。

1. 先写拒绝测试：默认关闭、未知工具、写操作、伪造运行、参数越界、权限撤销、需要审批。
2. 只允许 `knowledge_search`、`knowledge_read`，受信代码绑定用户、助手、会话和运行；模型不得传这些身份字段。
3. 执行前后复核活动运行、配置和权限。需要任何审批时拒绝，不能借旧包装器绕过审批。
4. 只记录受限审计字段，不写原始查询、文档内容、凭据或模型理由。
5. 使用临时知识库验证真实服务的检索、原文、引用链接、文档版本和撤权；不调用模型。

## 任务 3：官方客户端离线协议验证

文件：`scripts/verify_harness_sdk_protocol.py`、`server/tests/test_harness_protocol_smoke.py`。

1. 核对上游固定提交；使用源码中的官方 Python SDK，不下载运行时依赖。
2. 模拟通信对端验证初始化、普通消息走 `session/prompt`、原生审批默认拒绝、未知请求拒绝和会话事件过滤。
3. 明确报告 `fake-runtime-only`，不宣称启动了真实 Harness 或验证了模型。

## 验收与后续门槛

- 本阶段：上述新测试、现有审批/隔离/来源测试及客户端测试通过；需求状态和证据同步更新。
- 下一阶段：数据盘隔离 Node 运行时、锁定依赖、自有最小插件配置、环境白名单、单会话进程和关闭语义；全部验证后才能启动显式试点。
- 正式切换前：对话发送/停止/恢复、实时输出、模型路由、Tab、记忆/压缩、模型代审/双人审批、子代理、所有知识检索、图片图谱、产物和业务连接逐项通过等价测试。
- 官方 HippoRAG 仍单独推进可选后端；框架解耦不会将现有 lite 算法冒充完整复现。
