# 华微知行工作台 UI 第一版改造范围

分支：`feature/huawi-zhixing-ai-workbench-ui`

## 目标

在现有知行工作台前端上，围绕华微逐字稿中已经明确的制造业需求，建设“证据优先、低 Token、快响应”的 AI 能力层。保留既有 API、知识库、业务连接、来源追溯、审批边界和会话逻辑，不另做一套系统。

本分支的前端工作必须服务于两个可测量目标：

- 先判断业务域、流程、对象和指标，再取原始证据，避免整库和无关字段进入模型；
- 输入后立即反馈，首屏先显示状态结构，长请求可取消，失败可重试，支持局部刷新，并记录缓存/未缓存的 p50、p95 延迟和 Token 消耗。

华微原始逐字稿是需求优先级和验收口径；SAP/Joule 只提供企业级交互参考。

## 设计原则

- 先呈现业务结论，再展开来源、工具、Token、耗时和执行过程。
- 借鉴 SAP Fiori/Joule 的业务空间、对象导航和结果契约，不复制 SAP 品牌视觉。
- 不使用紫色渐变、发光球体或无业务意义的 AI 装饰。
- 成功、空结果、服务异常、会话失活、权限不足和重连都必须有明确状态。
- MCP 第一版默认只读；写入、审批和外部发送继续沿用现有权限与确认机制。
- 页面和结果服务于华微的真实业务任务，不虚构 KPI、Token 节省比例或 ROI。
- 对“Token 消耗过多”的具体原因保持可测量和可追溯，不把上下文、记忆或图片压缩等推测写成客户原话。

## 第一版范围

1. **首页**：业务助手、知识库、业务连接、近期任务和可核验状态的统一工作台。
2. **业务会话**：让结构化结果、来源、对象回跳、执行过程和成本信息更容易理解。
3. **MCP 接入**：连接、测试、工具发现、只读授权和绑定助手的路径更清楚。
4. **体验细节**：加载反馈、流式状态、错误恢复、空态、来源展开、短动效和响应感知。

第一轮只围绕两个真实只读业务场景落地；场景、字段白名单、标准答案、原方案基线和验收人由证据层冻结后再进入页面实现。

## 验收主线

`入口 → 自然语言问题 → 范围收敛 → 结构化结果 → Open / View More → 回到业务对象 → 来源/时间/权限/核验提示`

验收以华微逐字稿中的业务痛点和真实只读 MCP 场景为准；SAP 截图只作为交互和视觉参考证据。未取得真实 MCP、标准答案和客户基线前，不宣称性能改善或真实 Token 节省。
